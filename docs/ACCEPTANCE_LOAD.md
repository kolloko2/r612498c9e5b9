# Синтетическая нагрузочная приёмка

Дата измерения: 15 сентября 2026 года (Europe/Moscow). Этот отчёт заменяет
предыдущий прогон того же дня, в котором было получено 88,55 записи/с.

## Итог

| Конфигурация | Записей/с | Требование ≥100/с |
| --- | ---: | --- |
| SQLite, аудит безопасности включён | **149,02** | пройдено |
| SQLite, аудит выключен | 145,44 | пройдено |
| PostgreSQL 16 в Docker Desktop, аудит включён | 86,35 | **не пройдено** |

Отклик интерфейса при 100 пользователях, 20 одновременных сессий и формирование
отчётов укладываются в требования во всех трёх конфигурациях. Устойчивость к
30-секундному сетевому сбою по-прежнему не измерялась, задержка VoIP не измерялась.

Никакие реальные данные 112, внешние LLM, Voice API, звонки или экстренные службы
в тесте не использовались. Backend и Frontend запускались только на loopback,
`LLM_PROVIDER=mock`. Временные БД и журналы удалялись после прогона.

## Что изменилось с прошлого прогона

Журнал безопасности выполнял по два `fsync` на каждый HTTP-запрос, причём под общим
`RLock`: файл открывался и закрывался на каждую запись, а параллельные запросы
выстраивались в очередь. Измеренная стоимость — 2,917 мс на запись, то есть
потолок около 171 запроса/с независимо от остальной обработки.

`AuditLog` переведён на групповую фиксацию: writer-поток забирает все накопленные
записи, пишет их в один уже открытый файл и делает один `fsync` на группу.
Гарантия не ослаблена — `append` возвращает управление только после `fsync`,
включившего запись вызывающего, а при ошибке группы ошибку получают все её
участники. Результат микробенчмарка:

| Сценарий | До | После |
| --- | ---: | ---: |
| Одна запись, последовательно | 2,917 мс | 2,209 мс |
| 20 параллельных писателей | ~343 записи/с | 2 624,6 записи/с |

Прошлый прогон измерялся **без** `SECURITY_AUDIT_DIR`, поэтому прямое сравнение
88,55 → 149,02 некорректно: часть разницы относится к состоянию рабочего дерева и
хоста, а не к этой правке. Правка снимает узкое место именно в той конфигурации,
в которой работает поставляемый стенд, где аудит включён всегда.

## Конфигурация

- ОС: Windows 11 `10.0.26200`; CPU AMD Ryzen 5 5600 (6/12); RAM 31,92 GiB.
- Python 3.13; по одному Uvicorn worker на Backend и Frontend.
- PostgreSQL 16-bookworm в отдельном контейнере Docker Desktop, порт 127.0.0.1:55432,
  `synchronous_commit=on`, чистая база перед прогоном.
- Подготовка фикстуры вынесена за пределы измеряемых фаз.

## Почему PostgreSQL не достигает 100 записей/с на этом хосте

Замеры выполнены прямо против той же базы:

| Операция | Стоимость |
| --- | ---: |
| Транзакция с `fsync` (`synchronous_commit=on`) | 3,475 мс (287,7/с) |
| Та же транзакция без `fsync` | 0,826 мс (1 210,3/с) |
| Round-trip одиночного `SELECT` | 0,767 мс |

По `pg_stat_database` одно сохранение карточки порождает **6,44 транзакции**
(идентификация сессии, чтение карточки, чтение состояния диалога, запись, а также
захват и освобождение advisory-lease). Контрольный прогон с `synchronous_commit=off`
дал 121,33/с: отключение `fsync` не доводит показатель до уровня SQLite, значит
доминируют не задержки диска, а сами обращения к серверу.

Причина в том, что `backend/database.py` держит **одно** соединение с PostgreSQL и
сериализует все обращения процессным `RLock`. Это осознанная гарантия проекта:
advisory-lease кластера берётся на том же соединении, что и запись (см.
`docs/COMPLETION_BLOCK.md`). Следствие — параллелизма между 20 сессиями нет, и
пропускная способность равна 1 / (суммарное время обращений одного запроса):
6,44 × ~0,77 мс round-trip + один `fsync` ≈ 11,6 мс ≈ 86/с.

Это ограничение архитектуры соединения в сочетании со стоимостью round-trip и
`fsync` в виртуализованной среде Docker Desktop, а не алгоритмический дефект
обработки карточки: сериализация JSON и сам коммит измерены отдельно и дают
тысячи операций в секунду. Пул соединений для PostgreSQL снял бы ограничение, но
затрагивает гарантию «lease на том же соединении» и требует отдельного
архитектурного решения. Такое решение в рамках этой приёмки не принималось.

До его принятия:

- поставляемая конфигурация достигает требуемых 100 записей/с на SQLite;
- на PostgreSQL показатель следует перемерить на целевом Linux-сервере, где
  round-trip идёт через unix-socket, а `fsync` выполняется на физическом диске:
  оба измеренных здесь слагаемых там на порядок меньше. Результат этого хоста
  нельзя переносить на сервер ни в лучшую, ни в худшую сторону.

## Не проверено

- Устойчивость при задержке, потере и разрыве сети в течение 30 секунд:
  безопасного изолированного механизма network shaping для loopback-пары в этой
  сессии не было.
- Задержка передачи голоса (VoIP) ≤150 мс: требует измерения на реальном
  SIP/RTP-тракте, а не на mock-провайдерах.
- Несколько Backend workers/hosts, TLS, WAN, длительный soak, восстановление
  после отказа, реальный LLM, STT/TTS и физические телефоны.
- 100-user тест — конкурентный burst одного read endpoint, а не полная модель
  поведения пользователей в браузере.

## Воспроизведение

```powershell
# SQLite, конфигурация с аудитом (как на стенде)
python tools/acceptance_load.py --read-users 100 --write-sessions 20 `
  --offered-write-rate 150 --required-write-rate 100 --write-seconds 5 `
  --report-deadline 30 --security-audit --output "$env:TEMP\load-sqlite.json"

# PostgreSQL: база должна быть пустой перед прогоном
python tools/acceptance_load.py --read-users 100 --write-sessions 20 `
  --offered-write-rate 150 --required-write-rate 100 --write-seconds 5 `
  --report-deadline 30 --security-audit `
  --database-url "postgresql://user:password@host:5432/database" `
  --output "$env:TEMP\load-postgres.json"
```

Harness возвращает exit code 0 только если чтения и отчёты без ошибок, максимальная
задержка отчёта меньше лимита и завершённая скорость записи достигает порога.
`--database-url` и `--security-audit` добавлены в этой приёмке; без них harness
измеряет временную SQLite без журнала безопасности, то есть конфигурацию, которой
на поставляемом стенде не существует.
