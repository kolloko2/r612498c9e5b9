# План: исходящий запрос хода работ

Статус: базовый запрос обстановки реализован 23.09.2026.

Кнопка «Уточнить ход работ» обращается к назначенной бригаде. В текстовом режиме
возвращает наступившую вводную, в SIP — использует существующий голосовой доклад
с подтверждением воспроизведения. Повтор без новостей возвращает текущие сведения.
Это запрос фиксированного доклада, не свободный разговор с распознаванием любых
вопросов. Проверка реальным IP-телефоном остаётся отдельной аппаратной приёмкой.

Новые готовые карточки с бригадами отсчитывают оперативные этапы от назначения.
Сообщения заявителя и старые выданные карточки сохраняют отсчёт от поступления.
Лимит обработки фиксируется при выдаче: максимум из 180 с и суммы последней
оперативной задержки, времени реакции и 30 с на принятие. Это учебный бюджет.
В браузере пройден цикл до результата 12/12; регрессия проверяет отсутствие
будущих фактов, повторную доставку, принадлежность карточки и SIP без playback.

## Что уже находится в карточках и сценариях

В поставленном backend/data/tickets.json 96 черновиков. У 82 есть по пять updates,
у 14 updates пуст. Пример первого билета: выезд через 40 с, прибытие через 100 с,
работы через 160 с, завершение через 230 с и дополнительная информация заявителя
через 45 с. Это существующая авторская разметка, а не утверждённые заказчиком сроки.
Наличие updates не означает, что каждый билет методически проверен.

Update хранит id, after_seconds, source, text и необязательный unlocks_status.
В выданной карточке есть assigned_crew, situation_updates, planned_unlocks,
pending_phone_reports, field_report_calls. Приватный план не выдаётся ученику.
Существуют запуск телефонного доклада и подтверждение после успешного проигрывания;
только после подтверждения создаётся situation.update, разрешающее статус.

Первичный доклад в briefing.py решает другую задачу: передать адрес и происшествие
дежурному. duty_reply не получает состояние работ бригады, поэтому повторять этот
диалог для вопроса «Что на месте?» нельзя — ответ не будет связан с ходом событий.

## Целевая модель и дальнейшее развитие

1. **Единое состояние реагирования.** Для каждой карточки вычислять фактически
   наступивший этап и отдельно то, что уже сообщено диспетчеру. Для новых сценариев
   привязывать выезд и последующие этапы к назначению бригады/принятому первичному
   докладу, а не безусловно к моменту создания карточки. Старые сценарии явно
   сохраняют прежнюю временную привязку до авторской миграции.
2. **Два способа получить один факт.** Старший сообщает сам через существующий
   входящий доклад либо диспетчер нажимает телефон рядом с назначенной бригадой
   и выбирает «Уточнить ход работ». Никакого отдельного набора фиктивных статусов.
3. **Контекст ответа.** В диалог передавать только свою карточку, назначенную
   бригаду, текущий этап, доступные факты и историю уже переданных докладов.
   Будущие вводные, эталон и данные других карточек не передавать. В mock-режиме
   ответ детерминированный; LLM только формулирует подтверждённые сведения.
4. **SIP и получение сведений.** Переиспользовать Voice и существующую связку с
   карточкой. Один активный звонок на номер. Окончание TTS подтверждает доставку
   конкретного сообщения; после него фиксировать disclosure с ID исходной вводной.
   Входящий и исходящий пути дедуплицируются по одному update ID. Не засчитывать
   отклонённый звонок, неуслышанный ответ или оборванное воспроизведение.
5. **Оценка.** Время реакции на статус считать от получения факта диспетчером,
   а не от скрытого изменения обстановки. Отдельный критерий своевременности
   исходящего запроса вводить только при заданном преподавателем нормативе.
   Звонок сам по себе не изменяет статус службы — это действие обучаемого.
6. **Отказ и завершение.** До выезда можно ответить «Бригада ещё не направлена»;
   повторный запрос без изменений возвращает текущую обстановку. После остановки
   преподавателем новые звонки запрещены. Особые пути отказа/103 без бригады
   исключают ненужные будущие доклады.

## Что нужно подготовить в редакторе сценария

Для каждого этапа: условие наступления, задержка, говорящий, факты ответа,
разрешённый статус и ожидаемый комментарий. В предпросмотре преподавателя показать
временную последовательность и возможные ответы на запрос на каждом этапе.
Проверять достижимость: например, завершение на 230-й секунде нельзя сочетать
с обязательным завершением всей карточки за 180 секунд без изменения методики.
Факты заявителя нужно отличать от докладов старшего: не озвучивать их от имени
бригады только потому, что они лежат в одном массиве updates.

## Приёмка блока

- Входящий доклад и исходящий запрос раскрывают один и тот же наступивший факт.
- Ранний запрос не раскрывает будущий этап; несколько карточек не смешиваются.
- Без прослушивания новый статус не открывается; повтор не дублирует событие.
- Разрыв связи и остановка преподавателем не дают ложной отметки о докладе.
- Отчёт показывает время получения информации, действие диспетчера и задержку.

Отдельная внешняя система, брокер или новая БД для этого не нужны. Работа остаётся
в Workspace/Briefing и существующем Voice. Свободный вопрос-ответ со старшим
бригады требует отдельного расширения поверх реализованного запроса доклада.
